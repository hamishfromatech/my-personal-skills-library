# Comprehension Harm Evidence Base

This file holds the detailed empirical evidence from Balepour et al. (2026) supporting the `agentic-code-comprehension-decline-empirical` skill. All figures, tables, and findings are drawn from the study; short factual quotes are attributed where relevant.

## Primary Source

Balepur, N., Baumler, J., Chen, V., Choi, E., Rudinger, R., & Boyd-Graber, J. (2026). "(Im)Paired Programming: Coding Agents Improve Productivity but Harm Understanding." University of Maryland / New York University / Carnegie Mellon University. arXiv:2607.26375. Dataset and study materials open-sourced at https://github.com/nbalepur/impaired-programming.

## 1. Study Design

### 1.1 Participants

- **N = 54** computer science students (after dropping 5 who failed attention checks from 59 recruited across two U.S. colleges)
- Composition: 17 B.S., 31 M.S., 11 Ph.D. (of the 59 recruited)
- Self-reported coding experience: 5.4 ± 0.3 years in any language; 16.2 ± 1.4 months coding with AI (e.g., ChatGPT, Cursor)
- **Between-subjects design:** participants randomly assigned to one of two AI assistance conditions (Group A agent / Group B chatbot), 27 per group
- Background (BG) ability measured via pre-task multiple-choice quiz (HTML, CSS, JavaScript; 12 items targeting syntax recall, conceptual knowledge, code tracing, and implementation, drawn from LinkedIn skill assessments; a front-end engineer validated the questions)

### 1.2 Task: Zic-Zac-Zoe

An original game-creation task — a variation of tic-tac-toe called "zic-zac-zoe" — where users modify three files for page structure (HTML), game logic (JavaScript), and style (CSS). The game uses a 5×5 board with these rules:

1. Turns alternate between Player A/B, placing two symbols per turn (A → A → B → B → ...)
2. Clicking an unoccupied square displays the player's symbol ("A" or "B")
3. Game ends when a player occupies an entire row or column (not diagonals), or no more moves can be played (tie)
4. CSS must center the page horizontally
5. A status element shows the next turn ("Player A Turn" / "Player B Turn") and a message when the game ends ("A Wins!")

The task was chosen to be tractable in a single session (~50 min time limit, based on pilot testing with three Ph.D. students) but complex enough to require meaningful code structure. Users were not told they would later answer comprehension questions or extend their code (only 16% anticipated the extension task, confirming it was a surprise).

### 1.3 Two AI Conditions

Both groups used GPT-4.1 (gpt-4.1-2025-04-14) via an adapted VibeJam agentic coding UI (VSCode-like IDE with HTML/CSS/JS starter files, task description, website preview, and AI prompting panel).

| Condition | Tool | Behavior | Key Constraint |
|---|---|---|---|
| **Group A — Agent (direct-edit)** | **Aider** (open-source AI pair programmer, 44k+ GitHub stars) | AI directly edits files in the repository via search+replace diff blocks; user reviews and accepts/rejects diffs; agent summarizes executions | Agent has full access to user's code and project context |
| **Group B — Chatbot (guide)** | Generic LLM chatbot (ChatGPT-style interface) via litellm, 700 max tokens | Provides high-level code snippets only (max 5 lines, generic/non-project-specific); refuses to generate feature code, game logic, or UI components | No access to user's code; forces users to write code from scratch or manually adapt snippets |

The chatbot design mirrors how programmers adapt code from sources like StackOverflow while keeping the same prompt interaction paradigm as the agent, limiting non-compliance rife in no-AI studies.

**Prompt counts:** Agent users prompted 5.8 ± 0.4 times (initial task); chatbot users prompted 11.6 ± 2.5 times. In the extension task: agent users 6.8 ± 0.9; chatbot users 4.7 ± 0.6.

## 2. Comprehension Question Types (Bloom's Taxonomy Aligned)

After the initial task, users answered 12 comprehension questions (without seeing their code, apart from snippets shown in questions) tailored to their specific code. Questions were LLM-generated (GPT-5.2, structured decoding, max 3 retries) and linked to two Bloom's taxonomy levels: **recall** (Remember) and **reasoning** (Understand). Six questions of each type — two each for HTML, CSS, and JS.

### 2.1 Recall Questions (6 total)

| Sub-type | Format | What It Measures | Validation |
|---|---|---|---|
| **Multi-select identifiers** (3 questions) | Users select which HTML elements, CSS selectors, and JS functions exist in their code from a list of real + LLM-generated distractors | Factual recall of code components; identification of own code elements | Distractors generated by GPT-5.2 to mimic style/domain; two students answering without seeing code scored 0.38 (random = 0.5), confirming questions are not guessable from choices alone |
| **Code snippet identification** (3 questions) | Users pick which of two logically-equivalent JS/HTML/CSS code snippets exist in their code | Recognition of specific code the user wrote vs. plausible alternatives | Distractors introduce one noticeable but logically equivalent difference (e.g., swapped ID labels, different centering approach, 2D vs 1D array indexing) |

### 2.2 Reasoning Questions (6 total)

Multiple-choice questions probing causal reasoning about code behavior. Each question targets one of three main code snippets (HTML for status, CSS selector for page centering, JS function for board rendering), with two question types per snippet:

| Sub-type | Format | What It Measures |
|---|---|---|
| **Purpose questions** (3 questions) | "Which of these options best describes how the JavaScript code below uses the HTML element [status element]?" / "Which best describes the primary purpose of this function?" | Understanding of why code exists and what it does |
| **Change questions** (3 questions) | "If [ID] on the HTML element was changed to [new ID] but the rest stayed the same, what would most likely happen?" / "If this attribute was removed, what would happen to the elements?" | Counterfactual reasoning about how code changes affect behavior |

12 question templates were designed, then GPT-5.2 infilled them using the user's code. A front-end engineer reviewed templates; Author A validated infilling with five faulty and five perfect submissions. If a user did not attempt a specific criterion, no question was asked about it (GPT-5.2 checked for valid attempts).

### 2.3 Question Validation

- Recall question gold answers verified to exist in code: 99-100% pass rate (CSS selectors/JS functions), 94-95% (HTML features, human-validated subset)
- Code snippet identification: 98-100% pass rate
- Reasoning questions: 100% correct answers, 100% correct snippet extraction (agent users); one minor extraction error in chatbot users (4% rate, too rare to explain comprehension differences)
- Questions compared side-by-side across groups: no detectable differences in difficulty, distractor quality, question style, or multiple-choice writing flaws
- Comprehension scores align with self-reported ratings and low-effort interaction strategies, confirming questions measure "understanding" rather than a superficial construct

## 3. Extension Task Design

### 3.1 Procedure

After the initial task and comprehension questions, all participants completed an extension task **without the agent** (all used the chatbot, which requires active code writing). Agent users first completed a 5-minute warm-up task to familiarize with the chatbot interface. Time limit: 20 minutes (based on pilot testing).

### 3.2 Three New Criteria

Users started with their own submitted code from the initial task and had to extend it to pass:

1. **Corner win condition:** Add a win condition where players win by occupying all four corners of the board (for both Player A and Player B)
2. **Symbol coloring:** Style the board symbols so "A" symbols are red and "B" symbols are blue (defined in CSS, not set directly in JavaScript)
3. **Reset button:** Add a "Reset Game" button below the board that clears the board, resets to Player A's turn, resets the status display, does not refresh the page, and allows continued play

### 3.3 12-Rule Rubric and LLM Judge Validation

Extension task accuracy scored on a **12-rule rubric** (Rubric A.13 in the paper), covering: A symbol red color, B symbol blue color, colors in CSS not JS, Player A corner win, Player B corner win, original win conditions preserved, reset button visible below board, reset clears symbols and colors, reset resets to Player A turn, reset resets status display, reset does not refresh page, game accepts moves after reset.

Scoring via the same LLM judge as the initial task: **Gemini-3.1 Pro** (gemini-3.1-pro-preview) via litellm with structured decoding and medium reasoning effort. Other models tested (GPT-5.4, GPT-4.1, Claude Opus 4, Claude Sonnet 4) but Gemini had the best agreement.

**Validation:**
- Authors A and B manually scored 10 agent + 10 chatbot users' initial-task code via the rubric: agreed in **98% of rules**
- Gemini vs. Author A: **Cohen's κ = 0.96** (near-perfect agreement)

The initial task used a separate **15-rule rubric** with the same LLM judge and same validation procedure.

## 4. Regression Analysis Results

### 4.1 Model Specification

Linear regression predicting outcomes (initial accuracy, extension accuracy, comprehension) from BG ability, AI group, and their interaction:

```
y_out ~ β0 + β1·x_group + β2·x_bg + β3·(x_bg × x_group)
```

where x_group = 1 for chatbot, 0 for agent. This allows isolating how BG ability influences outcomes within each group (β2 for agents, β2 + β3 for chatbots).

### 4.2 Key Regression Findings

| Finding | Detail | Statistical Evidence |
|---|---|---|
| **BG ability predicts comprehension across both groups** | Higher background skill → higher comprehension, regardless of agent or chatbot use | Positive significant coefficient for BG ability in comprehension regression (Figure 5, middle) |
| **Initial accuracy does NOT predict comprehension** | Adding initial task accuracy to the comprehension model barely changes R² | Adjusted R² moves from **0.40 → 0.42**; initial accuracy coefficient is small and insignificant (Figure 6). Completion and comprehension are independent optimization goals |
| **Both initial accuracy and comprehension predict extension accuracy** | Adding both features to the extension regression produces large R² gains | Adjusted R² moves from **0.05 → 0.34** (Figure 7); both coefficients are significantly positive |
| **BG ability predicts initial accuracy only in chatbot group** | Agents equalize task accuracy across skill levels — novices match experts | BG coefficient significant for chatbot, not for agent (Figure 5, left) |
| **BG ability predicts extension accuracy only in chatbot group** | In agent group, scaffolding compensates for missing comprehension, masking who understands | BG coefficient significant for chatbot, not for agent (Figure 5, right; Adj. R² = 0.05 for agent extension) |

### 4.3 Interpretation

- Comprehension is **distinct from task completion**: a tool can excel at one and fail at the other
- Traditional coding skill remains the strongest predictor of comprehension even with agents
- Agent use masks BG differences in initial task output (novices match experts) but not in understanding
- The agent's scaffolding compensates for the user's missing comprehension in extension, creating a hidden dependency

## 5. Path Mediation Model Results

### 5.1 Model

A simplified saturated observed-variable path model estimated via robust maximum likelihood (MLR) using lavaan, summarizing relationships among background ability, condition (agent vs chatbot), code comprehension, initial accuracy, and extension accuracy. This model omits the BG × condition interaction from the primary regressions (individual path coefficients may differ numerically from primary analyses; the model is a compact summary of directional and mediational patterns).

```
Condition (Agent vs Chatbot)
  ├──→ Initial Accuracy (positive path) → Extension Accuracy (+)
  └──→ Comprehension (negative path) → Extension Accuracy (−)

Background Ability
  └──→ Comprehension (positive path) → Extension Accuracy (+)
```

### 5.2 Results: Opposing Indirect Pathways Offset

**For condition (Group):**
- Using the agent is associated with **higher initial accuracy** (positive mediator for extension)
- Using the agent is associated with **lower comprehension** (negative mediator for extension)
- Both mediators are positively associated with extension accuracy
- The two opposing indirect pathways **offset one another**, yielding a **non-significant total effect** of condition on extension accuracy
- No significant direct effect of condition on extension accuracy — the relationship is largely captured by the opposing mediated pathways

| Effect | Estimate | SE | 95% CI | p |
|---|---|---|---|---|
| Group: Direct on Extension Accuracy | -0.065 | 0.127 | [-0.184, -0.314] | < .608 |
| Group: Indirect via Initial Accuracy | -0.177 | 0.065 | [-0.050, -0.304] | < .006 |
| Group: Indirect via Comprehension | -0.204 | 0.069 | [-0.340, -0.069] | < .003 |
| Group: Total Indirect | -0.027 | 0.114 | [-0.250, -0.196] | < .810 |
| Group: Total Effect | -0.038 | 0.103 | [-0.163, -0.239] | < .712 |

**For background ability:**
- Significant total effect on extension accuracy via an indirect pathway through code comprehension
- Higher BG → higher comprehension → higher extension accuracy
- No significant direct effect of BG on extension accuracy
- No significant indirect effect through initial accuracy
- The association is primarily reflected in the comprehension pathway

| Effect | Estimate | SE | 95% CI | p |
|---|---|---|---|---|
| BG: Direct on Extension Accuracy | -0.120 | 0.254 | [-0.619, -0.378] | < .636 |
| BG: Indirect via Initial Accuracy | -0.138 | 0.105 | [-0.069, -0.344] | < .192 |
| BG: Indirect via Comprehension | -0.514 | 0.176 | [-0.169, -0.859] | < .003 |
| BG: Total Indirect | -0.652 | 0.186 | [-0.287, -1.017] | < .001 |
| BG: Total Effect | -0.531 | 0.237 | [-0.067, -0.996] | < .025 |

### 5.3 Interpretation

This is the strongest evidence that the agent **trades understanding for scaffolding**. The agent produces better initial code (helping extension) but worse comprehension (hurting extension), and these forces cancel — producing statistically similar extension accuracy that hides a structural dependency. The user is now dependent on the agent to extend the very code the agent produced.

## 6. Interaction Strategy Coding

### 6.1 Agent Prompt Strategies (4 strategies)

Author A reviewed 10 users' prompts and after two rounds discovered four high-level strategies. Gemini-3 Flash labeled a strategy for all 152 agent prompts. Validation: Author A and B each labeled 50 random prompts (90% agreement); Gemini and Author A agreed in 94% of cases.

| Prompting Strategy | Description | Comprehension (↑) | BG Ability | # Users | Proportion Used |
|---|---|---|---|---|---|
| **Turning criteria into syntax** | User mentions specific HTML/CSS/JS syntax (tags, function names, selectors) rather than natural language (e.g., "Broadcast statusMessage to a p tag under the h1 tag") | **0.743** (highest) | 0.684 | 9 | 0.087 |
| **Iterative debugging** | User asks AI to refine or debug an initial mistake (e.g., "Now there is a problem where it only shows player B...") | 0.692 | 0.662 | 5 | 0.040 |
| **Copying criteria** | User directly copies task criteria verbatim or nearly verbatim (e.g., "Add a status element in a paragraph tag...") | 0.654 | 0.668 | 25 | 0.793 |
| **Asking for explanations** | User asks AI to summarize the codebase or explain it (e.g., "First, explain the whole project") | 0.635 (lowest) | 0.692 | 6 | 0.046 |

**Regression confirmation (Appendix A.4):** Positive coefficients for intercept (0.714) and BG ability (0.569); negative coefficients for proportions of copy (-0.469), exploratory (-0.745), and debugging (-0.338) prompts. Users who increase technical prompt proportions tend to have higher comprehension.

**Takeaway:** Users who add code syntax to prompts comprehend best; copy-paste prompts (the most common strategy, used 79% of the time) produce the lowest comprehension. Low-effort prompting is a detectable, classifiable signal.

### 6.2 Agent Review Strategies (4 strategies)

When agents edit code, users can interact in four ways. Coded by observed behavior across the multi-turn interaction.

| Review Strategy | Description | Comprehension (↑) | BG Ability | # Users | Proportion Used |
|---|---|---|---|---|---|
| **Hit Accept (Each file)** | Accept changes individually by clicking "Accept" per file — per-file review | **0.777** (highest) | 0.714 | 7 | 0.136 |
| **Hit Accept (All)** | Accept all changes by clicking "Accept All" — bulk accept | 0.664 | 0.669 | 20 | 0.492 |
| **Override Changes** | Override via manual edits or clicking "Reject" | 0.661 | 0.682 | 15 | 0.318 |
| **Auto-Accept** | Prompt again to auto-accept changes without reviewing | 0.615 (lowest) | 0.603 | 6 | 0.053 |

**Regression confirmation (Appendix A.4):** Positive coefficients for intercept (0.475) and BG ability (0.509); negative coefficients for proportions of Auto-Accept (-0.334), Overriding (-0.214), and Click Accept All (-0.159). Users who more often review each file's changes tend to have higher comprehension.

**Takeaway:** Per-file review yields the highest comprehension (0.777) but still does not fully reach chatbot comprehension levels. Auto-accept yields the lowest (0.615). Even partial review recovers most of the comprehension gap — making review UX a high-leverage design lever.

### 6.3 Chatbot Prompt Strategies (7 strategies, Appendix A.10)

For comparison, qualitative coding of chatbot prompts revealed seven strategies. Users who actively request high-level guidance (snippets, design suggestions, syntax help) tend to have higher comprehension than those who attempt to use the chatbot to complete tasks for them (debugging, jailbreaking).

| Prompting Strategy | Comprehension (↑) | BG Ability | # Users |
|---|---|---|---|
| Snippet request | 0.853 | 0.658 | 9 |
| Design help | 0.834 | 0.626 | 14 |
| Syntax help | 0.826 | 0.645 | 21 |
| Clarification | 0.811 | 0.580 | 11 |
| Debugging | 0.781 | 0.492 | 5 |
| Jailbreaking (bypassing refusal) | 0.755 | 0.569 | 5 |
| Frustration | 0.583 | 0.462 | 1 |

## 7. Code Readability Metrics

### 7.1 Metrics and Implementation

Analysis focused on agent users' final JavaScript file (hosts most of zic-zac-zoe's logic). Four standard readability metrics from Posnett et al. (2011), implemented via Python's splitlines() and the Esprima JavaScript tokenizer:

| Metric | Definition | Implementation |
|---|---|---|
| **Lines of code (LOC)** | Total lines in the JS file | Python splitlines() |
| **Entropy** | How evenly tokens are distributed (higher entropy = more variety) | E = Σ pⱼ · log₂(pⱼ), where pⱼ is each unique token's proportion of presence |
| **Volume** | Total information via unique token count (Halstead volume) | V = N · log₂(n), where N = total operators+operands, n = unique operators+operands |
| **Comment proportion** | Proportion of lines with comments | Comment lines (detected by Esprima) / LOC |

Four separate regressions were fit (predicting comprehension from each metric) due to high collinearity among metrics. All metrics were z-score normalized.

### 7.2 Results: All Negatively Correlated with Comprehension for Agent Users

| Readability Metric | Relationship to Comprehension (Agent Users) | Direction |
|---|---|---|
| **Lines of code (LOC)** | Fewer lines → higher comprehension | Negative |
| **Entropy** | Lower entropy → higher comprehension | Negative |
| **Volume** | Lower volume → higher comprehension | Negative |
| **Comment proportion** | Fewer comments → higher comprehension (counterintuitive) | Negative |

**Interpretation:** Agent users better digest concise code without distracting comments. This is consistent with past AI coding interviews where verbose comments obscured rather than clarified. More comments may signal that the agent (not the user) wrote explanatory text the user never engaged with.

### 7.3 Agent vs Chatbot Code Comparison

| Group | Lines | Volume | Entropy | # Functions | Comment Line Proportion |
|---|---|---|---|---|---|
| **Agent (initial task)** | 124.89 ± 3.61 | 3929.71 ± 91.15 | 5.40 ± 0.01 | 8.30 ± 0.31 | 0.13 ± 0.01 |
| **Chatbot (initial task)** | 83.08 ± 5.27 | 2786.78 ± 211.53 | 5.21 ± 0.06 | 7.46 ± 0.40 | 0.07 ± 0.01 |
| **Agent (extension task)** | 144.79 ± 4.91 | 4870.47 ± 159.62 | 5.40 ± 0.02 | 9.17 ± 0.36 | 0.12 ± 0.01 |
| **Chatbot (extension task)** | 103.56 ± 6.91 | 3765.15 ± 287.88 | 5.26 ± 0.06 | 9.07 ± 0.54 | 0.07 ± 0.01 |

Agent users tend to write longer, more complex code with more comments — likely because the agent completed more task requirements, producing more code overall.

### 7.4 Design Implication

Concise, readable agent output helps comprehension; bloated output harms it. Readability is a trainable signal: agents can be optimized to produce fewer lines, lower volume, and concise comments. Guard against reward-hacking (e.g., collapsing code into unreadable one-liners to minimize LOC).

### 9.2 The Preference Paradox

Users find the agent more helpful and simpler (less mental effort) than the chatbot, but recognize weaker understanding. Despite this, users prefer the agent — but most prefer having the option to switch between the AIs. Users will not self-correct: subjective preference actively misleads — the tool that feels best (fast, low-effort) is the one that harms understanding most.

### 9.3 Perceived vs Measured Understanding (Appendix A.6)

Likert ratings normalized to 0–1 scale and fit with linear regression against measured comprehension and extension accuracy:

| Attribute | p | Adjusted R² | Coefficient |
|---|---|---|---|
| Comprehension | < .001 | 0.327 | 0.467 ± 0.181 |
| Modifiability | < .001 | 0.203 | 0.694 ± 0.366 |

Users' subjective perceptions align with their actual outcomes — they have some awareness of their comprehension gap, but this does not change their preference.

### 9.4 Qualitative Feedback Themes (Section 6.2)

Four common themes from open-ended feedback:

1. **"Who Needs to Think"** — Coding with agents required little mental effort. "I didn't have to think at all" (U10). Users didn't need website or CS knowledge (U15, U49); the agent had file context (U31) allowing "fuzzier instructions" (U35). Website preview meant no desire to review changes (U27, U54). U46 rarely reviewed despite knowing it would be "detrimental in the long run."

2. **"Agents Can Get Out of Control"** — Agents "change somewhere unexpected or even destroy the original functions" (U16), impairing understanding. Agent eagerly included unneeded features (U3), obscuring the code.

3. **"Make Code Quality Actionable"** — Extension was easy when agents wrote high-quality code (comments U44/U54, modular structure U5/U46, well-named functions U21). But benefits resembled onboarding vs. understanding: "Comments made it easy to understand where to add new features, but having not fully reviewed the code made it much harder to understand everything" (U31).

4. **"Understanding is Polarizing"** — Users were split. U57 wished the agent "made me understand where code is supposed to go," but most praised agents' accuracy and speed. For chatbot users, U28 felt it "really helped remember how to use the code later on," but others rejected it: U5 said "It's totally useless" and U49 asked "What's the point of learning all this when the AI can build it out for you?"

## 10. Limitations

The authors explicitly acknowledge the following limitations:

1. **Student population:** N=54 CS students (17 B.S., 31 M.S., 11 Ph.D. of the 59 recruited; 5 dropped for failed attention checks) at two U.S. colleges. May not fully generalize to professional developers with more experience or domain expertise, though background skill was controlled. Users reported 5.4 ± 0.3 years coding experience and 16.2 ± 1.4 months coding with AI.

2. **Web development domain:** The study focuses on web development (HTML/CSS/JS), one of the most common coding agent use cases. Comprehension effects may vary by task complexity, domain, or codebase size. The authors encourage extending the protocol to other domains (algorithmic design, data analysis).

3. **Single task:** One website-building task (zic-zac-zoe) plus one extension task. Comprehension measured immediately after the task; long-term retention and cumulative comprehension debt not assessed. The authors call for longitudinal studies via comprehension quizzes every n projects.

4. **Two-condition design:** Only agent (Aider) vs chatbot; does not test intermediate modes (e.g., agent with forced review prompts, agent with cognitive forcing functions). Aider is one specific agent; results may vary with other agents (Cline, Cursor Agent, Claude Code) with different interaction models.

5. **Interface constraints:** The VibeJam-adapted UI supports fewer workflow customization features than developers typically use in practice. Future research could test whether results hold for users working with coding agents they choose (Cursor, Codex) via proctored sessions or IDE plugins.

6. **Reliance on NLP tools:** The study relies on LLMs to generate comprehension questions, label prompt strategies, and judge code submissions. Despite checks (front-end engineer review, manual validation, author-LLM agreement with Cohen's κ = 0.96), errors may have slipped through. Appendix A.9 rigorously analyzes LLM-generated questions and detects no major issues.

7. **Self-report reliance for preference:** Subjective ratings are subject to social desirability and post-hoc rationalization, though the comprehension gap is objectively measured.

8. **Short-term productivity may be sufficient in some cases:** The authors acknowledge that for personal projects just for fun (vibe coding a personal website), short-term productivity may be sufficient. However, many novices attempt these projects to gain realistic programming experience, so coding agents that jointly improve productivity and understanding would still help these users.

| Finding | Statistic | Significance |
|---|---|---|

## 12. Design Directions for Comprehension-Supporting Agents

1. **Dissuade low-effort prompting:** Classify and refuse "lazy" copy-paste prompts; nudge users to rewrite in technical terms. Requires low-effort prompt classifiers and post-training refusal methods.
2. **Active engagement during review:** Replace passive "Accept All" with per-file review workflows; design interactions that force cognitive engagement rather than passive acceptance.
3. **Generate readable code:** Optimize agents for code readability metrics (LOC, entropy, volume, comment proportion) beyond task completion. Guard against reward-hacking (unreadable one-liners).
4. **Make understanding benefits explicit:** Users don't inherently value understanding; agents should surface when understanding matters (debugging, handoffs, outages, agent unavailability).
5. **Route between user and AI:** Predict when AI or user should implement code to balance productivity and understanding. Users prefer having the option to switch (hybrid 4.6/5).
